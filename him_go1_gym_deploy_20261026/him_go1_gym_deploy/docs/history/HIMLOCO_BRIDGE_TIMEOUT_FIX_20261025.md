# HIM 桥接命令超时：多线程计时竞争修复

日期：2026-10-25。首轮悬空标定日志 `him_suspended_20261025_180110_13712.jsonl` 在 CALIBRATE 开始约 0.44 s 后停止。终端 A 原因：`policy command timeout`。R2 上升沿已识别；不需要长按 R2，HIM 策略尚未运行。

## 确认存在的缺陷

旧版 C++ 在控制线程和 LCM 命令回调线程中分别先读取 `steady_clock`，然后才进入 Guard 的互斥锁。若控制线程较早取到时间后被暂时挂起，命令线程先入锁并记录了稍晚的接收时间，控制线程随后入锁时就会出现 `now < last_command_time_`。旧 `expireLocked()` 将它报告为命令超时。反向交错还可能使状态时间检查误报。

用完全离线的最小程序复现了：最新命令实际只经过 10 微秒，也会报 `policy command timeout`。该程序、修复前头文件保存在 `audit/20261025_fixes/reproduce_bridge_clock_order.cpp`、`bridge_guard_before_clock_fix.hpp`。没有连接 SDK、LCM 或机器人。

本次实机日志已记录的主循环间隔为约 20 ms，控制计算最大约 6.1 ms，与上述问题相容。旧版没有记录桥接端触发时的实际命令年龄，故无法仅凭旧日志排除真实通信或调度停顿。

## 修复

- Guard 自己在获得互斥锁后读取单调时钟；调用者不再传入预先捕获的时间。时间检查和更新遵循同一锁的顺序。
- SDK 状态的源时间戳继续用于消息配对和回显，不充当线程接收时间。
- 桥接锁定停止时打印 `command_age_ms`、`state_age_ms` 和 `last_command_id`，便于区分后续真实超时与其他原因。
- 保留状态 50 ms、命令 100 ms 超时、时间戳/序号检查、L2、PositionLimit、PowerProtect 和停止锁存。
- 策略权重、观测、动作缩放、PD 增益、标定过程和 Python 策略逻辑没有改变。
